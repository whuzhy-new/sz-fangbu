## 起终点一致性修正

科苑 C 口到 T2 的复测结果：

| 查询方式 | 距离 | API 秒数 | 按当前规则计时 |
| --- | --- | --- | --- |
| 仅旧入口坐标 | 179 米 | 143 秒 | 2 分钟 |
| T2 地点 ID | 254 米 | 203 秒 | 3 分钟 |

用户手机高德显示约 255 米、4 分钟。加入相同地点 ID 后，路径与手机截图基本对应；API 秒数与 App 显示分钟仍不完全一致。保留用户要求的逐段四舍五入规则，不把 App 的整数分钟当作 API 原始秒数。申请截图需核对高德实际页面。

[高德路径规划 2.0 文档](https://lbs.amap.com/api/webservice/guide/api/newroute)中，步行支持 `origin_id` / `destination_id`；公交地铁的 `originpoi` / `destinationpoi` 必须成组；普通自行车按坐标查询。

二维码只携带实际参与计算的地点 ID。仅有地点标签、旧数据中的附加 POI 字段、或自行车坐标方案，都不能在扫码时额外切换到 POI 路线。站间地铁仍明确指定首末站 POI。

## 重算方式

```sh
.venv/bin/python scripts/data/retarget_office.py \
  --office-config data/office-profiles/shenzhen-bay-t2.json \
  --snapshot innovation-t2-entr-location-2026-11-09 --apply
```

不传 `--apply` 时只写入 `work/office-retarget/`，可先检查再切换。脚本校验快照、终点身份及其他工区的数据；全部完成后才替换当前文件，运行失败会保留当前版本。快照已存在时不会用新数据覆盖。同一完整版本已应用时不重复请求接口。

- 复用原有有向 OSM 路网、车站与站口坐标，以及明确指定首末站的高德 API 缓存。
- 重新比较旧方案涉及的到达站，以及 T2 周围 3.5 公里内候选站的各个出口与接驳方式。
- 图上的候选组合须有站到站 API 结果，才进入固定方案；图推导本身不作为核验依据。
- 仅重算深圳湾的步行、自行车、地铁范围，替换深圳湾的自行车空间校准样本，重新核对既有验证地点和小区补全依据。
- 保留共享自行车接驳倍率，避免只改一个终点却改变所有工区的本地路网权重。
- 景湖与太子的配置、方案、范围、校准样本和验证记录保持一致；生成报告记录数据复用、查询数量与新旧终点。

地图仍为预估范围；地址核验依次查询步行/自行车、完整地铁、分段地铁。分段保留站内换乘，每段先按分钟四舍五入再相加。不同候选站与高德返回方案的筛选仍有局限，不能视为穷举所有可能路线。
